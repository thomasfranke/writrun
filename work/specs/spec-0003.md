# spec-0003 — Title mirror Issues by task tag

**References:** [task-0006](../tasks/task-0006.md)

## Scope

The mirror's title moves from `task-NNNN — <title>` to
`[TASK-NNNN] <task title>`, and every place that finds a mirror by its
title moves with it.

In scope: `mirror_issues.sh` (minting, duplicate detection, the
foreign-mirror guard), `reflect_progress.sh` (mirror lookup), and a
one-time retitle of the mirrors that already exist. Out of scope: labels
and their lifecycle — `status:*` and `writrun:task` are untouched — and
the mirror body.

## Steps

1. `mirror_issues.sh`: mint new mirrors titled `[TASK-NNNN] <task
   title>`; match existing mirrors by the tag, still recognising the old
   `task-NNNN ` prefix so pre-rule mirrors are found, not duplicated.
2. `reflect_progress.sh`: resolve a task's mirror by the tag, with the
   same old-prefix fallback.
3. In the implementing change, retitle the existing mirrors to the tag
   form — the Issue is a projection, so retitling it rewrites no
   authority.

## Acceptance criteria

- When a merged task gains its mirror, the system shall title it
  `[TASK-NNNN] <task title>`.
- When the machinery looks a mirror up and only an old-form title
  exists, the system shall find it and shall not create a duplicate.
- When a foreign Issue carries a tag-shaped title for an id the queue
  does not own, the foreign-mirror guard shall keep refusing to touch
  it.
- When the implementing change lands, every existing mirror shall carry
  the tag-form title.

## Edge cases

- A task title that itself contains a bracketed tag-shaped string.
- Case: the tag is uppercase, the file id lowercase — lookups map one to
  the other.

## Tests required

One case per criterion, in the mirror and reflect suites.

## Definition of Done

- `make tests` green, including the new cases.
- `make template-sync` changes nothing beyond the synced copies.
- No permanent doc touched.

## Proposed product changes

none — the authoring change updated `product/pipeline.md` first.

## Outcome

Built as planned. The mint writes `[TASK-NNNN] <task title>`, and both
title-based lookups — `issue_row_of` in `mirror_issues.sh`, the mirror
resolution in `reflect_progress.sh` — read the tag and the
`task-NNNN — ` prefix that predates it. The suite went from 162 to 169
case files.

The one-time retitle is done: all 13 existing mirrors (#5, #6, #7, #10,
#12, #19, #21, #23, #25, #27, #30, #32, #33) now carry the tag form,
including the closed ones, since a lookup reads titles in any state.

Four divergences, three of them from following the same reasoning the
existing code already used:

- **Lookups match on the number, not the title text.** Step 1 said
  "match existing mirrors by the tag, still recognising the old prefix",
  which reads as two string comparisons. `issue_row_of` used to compare
  text (`case "$t" in "$1 "*`), and that made width part of identity —
  a mirror titled `task-004 — ` was invisible to an id spelled
  `task-0004`. `reflect_progress.sh` already matched on the number for
  exactly this reason. Both now parse the id out of either title shape
  and compare numerically, so `[TASK-5]`, `[task-0005]` and
  `task-005 — ` are one task.

- **The tag keeps the id's own width.** The criterion says
  `[TASK-NNNN]`, and a historical `task-004` would have to be padded to
  match that literally. It is not: a mirror is a projection of the file,
  never a correction of it, and the schema already tolerates the widths
  history left. Matching on the number is what makes the padding
  unnecessary.

- **`LIVE_IDS` became `LIVE_NUMS`.** The orphan sweep compared the
  title's first word against a list of ids — a comparison that only
  worked because the title *was* the id followed by a space. With the
  tag form the first word is `[TASK-0006]`, so the sweep now parses the
  id like every other lookup and compares numbers. The variable was
  renamed rather than kept alongside, because a second list holding the
  same information in a shape nothing reads is how the next reader gets
  it wrong.

- **The retitle was run as a one-off, not shipped as a script.** Step 3
  says "in the implementing change, retitle the existing mirrors"; it
  does not say to leave machinery behind. A migration that can only run
  once is not machinery this project keeps — the command and its result
  are recorded here instead, which is the durable form. The mirrors it
  touched are listed above.

**One consequence step 3 did not anticipate, and it is live right now.**
`writrun-progress` runs on `pull_request_target` and executes the *base
branch's* copy of `reflect_progress.sh`. Retitling the mirrors before
this change merges therefore hid them from the script currently on
`main`, which knows only the old prefix: the run for this task's own pull
request reported "No mirrored Issue for task-0006", and mirror #7 is
parked at `status:in-progress` instead of moving to `status:in-review`.

The window is the gap between the retitle and this merge, the cost is
stale labels and nothing else — no authority lives in a mirror — and it
closes on merge, when `main` gains a script that reads both forms. The
ordering is inherent to a step that mutates the forge ahead of the code
that understands the mutation; the alternative, retitling after the
merge, trades a visible stale label for a step somebody has to remember.
Worth stating plainly for the next task that migrates the mirror: **the
forge and the base branch move at different times, and the base branch
is what runs.**

The foreign-mirror guard needed no change and got none: ownership is the
body's "Introduced by" line, never the title. That is now load-bearing
in a way it was not before — the lookup finds strictly more mirrors than
it used to, so the guard is the only thing standing between a tag
collision and an adopted mirror. Its case was rewritten to carry a
tag-shaped title for exactly that reason.
