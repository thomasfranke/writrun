# spec-0004 — Record approval on the merge

## Scope

`writrun approve` stops listening for an approving review and starts
listening for a merged pull request, writing the `draft → approved` flip
to `main` instead of to the pull request's branch.

In scope: `.github/workflows/writrun-approve.yml` (trigger, authority
condition, checkout, commit target) and the cases that cover it. Out of
scope: `flip_approved_specs.sh`, which selects specs from a diff range
and is indifferent to what triggered it; `check_state.sh` rule A, which
must keep forbidding a pull request that approves its own spec; and
`check_recorded_approvals.sh`, which stays as the guard on an approval
hand-written *inside* a diff — the new flow never writes one there, so it
should simply fall silent.

## Steps

1. Trigger: `pull_request_target` with `types: [closed]`, guarded by
   `github.event.pull_request.merged == true`. `pull_request_target` and
   not `pull_request`, because only the former carries a write token when
   the head is a fork — which is what lets this serve fork pull requests
   that the review-based flow had to skip entirely.
2. Authority: drop the `author_association` filter. The forge only lets
   an account with write access merge, so the merge *is* the proof the
   review filter was standing in for; keeping a second test would assert
   something already guaranteed.
3. Checkout the base branch at its post-merge tip, and derive the range
   the flip reads from the merge itself — the pull request's base sha
   against the merge commit — rather than from a head branch that the
   merge may already have deleted.
4. Commit and push to the base branch. Restate in the workflow header
   what this now depends on: `main` accepting a push from the Actions
   token, which today it does because it is unprotected.
5. Cover the flow's own silence: `check_recorded_approvals.sh` must stay
   quiet for a merge-recorded flip, since nothing in any pull request's
   diff carries the transition.

## Acceptance criteria

- When a pull request that adds a draft spec is merged, the system shall
  record that spec as `approved` on the base branch.
- When a pull request is closed without merging, the system shall record
  nothing.
- When the merged pull request came from a fork, the system shall record
  the flip exactly as for a branch in this repository.
- When a merged pull request carries no spec the flip qualifies, the
  system shall push no commit.
- When a pull request's diff itself moves a spec `draft → approved`, the
  system shall keep rejecting it — the merge records the transition, and
  a pull request never carries it.

## Edge cases

- The head branch deleted by the merge: nothing may read it.
- A merge whose flip commit lands while another push is in flight — the
  push is a fast-forward or it is retried, never a force.
- A spec the pull request returned `approved → draft` (an amendment)
  flips back on the same merge, as it does today.

## Tests required

One case per acceptance criterion, in the `flip_specs` and
`recorded_approvals` suites. The workflow's YAML condition is not
executable by the suite; the case that covers it is the range derivation,
which is.
