# spec-0005 — Label a proposed task apart from a queued one

## Scope

`status:proposed` becomes the label of a task an open pull request
proposes; `status:pending` keeps only the meaning its description already
claims — in the queue, a spec not yet approved.

In scope: `mirror_issues.sh` (the label decision, the `ensure_label`
declarations, the reopen path) and its suite. Out of scope: the task
schema, which gains no status; `list_tasks.sh`, which reads files and
never labels; and the retirement of a mirror when its pull request closes
unmerged, which already works and must keep working unchanged.

## Steps

1. Declare `status:proposed` alongside the others at open, with a
   description that says what it means: a pull request proposes this
   task; it is not in the queue yet.
2. Correct the `status:pending` description, which today claims "Task
   exists" for issues where the task does not exist yet — after this
   change the claim becomes true, and the text should say so plainly.
3. Split the one condition that conflates the two states
   (`if [ "$open" = "true" ] || ! is_ready $refs`) into the three real
   outcomes: open → `status:proposed`; merged and not ready →
   `status:pending`; merged and ready → `status:ready`.
4. The reopen path relabels a mirror whose pull request came back; a
   reopened pull request is open, so it relabels to `status:proposed`.
5. The mirror body already promises "Becomes ready for development when
   #N merges and every spec is approved" — keep it true against the new
   vocabulary.

## Acceptance criteria

- When a pull request that adds a task is opened, the system shall label
  its mirror `status:proposed`.
- When that pull request merges with a spec still `draft`, the system
  shall relabel the mirror `status:pending`.
- When that pull request merges with every spec `approved`, the system
  shall label the mirror `status:ready`.
- When a merged pull request creates a mirror that never existed, the
  system shall label it by the same merged rules, never `proposed`.
- When a pull request that was closed unmerged is reopened, the system
  shall relabel its mirrors `status:proposed`.
- When a pull request closes unmerged, the system shall keep retiring its
  mirrors as it does today.

## Edge cases

- A mirror carrying a hand-added label that is not a `status:` one keeps
  it — relabelling replaces the status, not the rest.
- An adopting project that already uses `status:pending` on its own
  issues: the `writrun:task` filter still decides what is touched.

## Tests required

One case per acceptance criterion, in the `mirror_issues` suite.

## Definition of Done

- `make tests` green, including the new cases.
- `make template-sync` changes nothing beyond the synced copies.
- No permanent doc touched.
