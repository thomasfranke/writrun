# the task tag leads the title, one bracket per task.

**2026-08-28**

[0045](0045-one-decision-per-file.md)'s sibling change put the
`[TASK-NNNN]` tag at the *end* of a pull request's title, after the
Conventional Commit summary, and used a comma form — `[TASK-0012,
TASK-0014]` — when a change carried several. Both are reversed here: the
tags lead, and each task gets its own brackets with no separator —
`[TASK-0012][TASK-0014] feat(mirror): …`.

The reason is where the title ends up. Squash-only means the title *is*
the commit subject on `main`, and a subject is read at its left edge —
in `git log --oneline`, in a blame, in a release note. A tag at the end
is a tag behind whatever truncation the reader's terminal applies, which
is the one position guaranteed to hide it. What work this was belongs
before what kind of change it was.

One bracket per task rather than one bracket holding a list: `grep -F
'[TASK-0012]'` then finds every commit for that task whether it rode
alone or with siblings, which the comma form quietly broke — the same id
appeared as `[TASK-0012]` in one title and `TASK-0012,` inside another.

The prefix sits outside Conventional Commits' grammar, and that is
accepted deliberately: nothing here parses subjects mechanically. The
`type(scope):` convention survives for people reading, `git log --grep`
serves the machine, and the release notes are generated by the forge from
pull requests, not by parsing subjects. Rejected: keeping the trailing
position and teaching readers to look for it — the position was chosen
for grammar-compliance nobody was enforcing, at the cost of the one
property the tag exists for.
